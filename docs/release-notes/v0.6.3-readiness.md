# v0.6.3 retained telemetry and readiness

This patch integrates retained-history query fixes, bounded ingestion and trace
reads, explicit SQLite FTS provisioning, and the Kubernetes resource partition
used in the local r4 run. Authentication remains optional under the existing
open-access contract; HTTPS termination at the configured proxy is unchanged.

## Upgrade and backfill

Stop application writers and take a restorable backup before upgrading. Preserve
SQLite databases and their WAL/SHM files coherently, including the separate
aggregate database. Allow free disk for index creation, FTS backfill, rollup
storage and WAL growth.

Run the new binary's `otelcontext migrate up` against the intended main database
with the runtime's `LOG_FTS_ENABLED` setting, then `otelcontext migrate status`.
The main ledger stays at schema 4. With `LOG_FTS_ENABLED=true`, `migrate up` also
installs or repairs the managed SQLite FTS objects and backfills existing logs,
even if the versioned schema is already exact. Startup with
`DB_AUTOMIGRATE=false` requires the exact schema and configured FTS objects;
it refuses missing or incompatible objects instead of repairing them. Setting
`LOG_FTS_ENABLED=false` retains the LIKE search path and leaves existing FTS
objects alone. See [migration ownership](../../internal/migrate/runner.go).

Aggregate startup adds indexes and derived hourly/service-summary tables while
preserving the store UUID, authoritative rows and aggregate schema version.
Index or derived-schema setup failure refuses startup. Background work builds
eligible retained hours and resumes incomplete work after restart. Until a
usable summary is published, reads fall back to the authoritative five-minute
rows. Backfill consumes CPU, I/O and disk; startup completion does not mean that
historical acceleration is complete. See the
[rollup worker](../../internal/aggregate/rollup.go) and
[service summaries](../../internal/aggregate/service_summary.go).

For an upgrade from before v0.6.2, also follow the
[schema-4 retention migration instructions](v0.6.2-retention.md). Retain the
pre-upgrade backup for rollback. Restoring it discards later writes; do not remove
migration ledger entries or enable aggregate rebuild to bypass compatibility.

## Current local acceptance and existing evidence

The [production-200 profile](../../test/loadsim/README.md#current-production-200-acceptance-targets)
uses 200 services and 20 simulated hosts. The configured stack is 4 CPU/8 GiB,
partitioned as app 3 CPU/6 GiB and Prometheus 1 CPU/2 GiB. The migration init
container is limited to 3 CPU/4 GiB, so the app pod's effective limit remains
3 CPU/6 GiB. OS, Kubernetes and injected Istio overhead are additional.
`GOMAXPROCS=4`, `GOMEMLIMIT=3GiB`, application disk budget 14,336 MiB, aggregate
budget 6,144 MiB, and PVC sizes 16 GiB plus 32 GiB remain unchanged.

On October 20, 2026, the user closed latency diagnosis and changed sustained
ACK p99 acceptance from 500 ms to **600 ms inclusive**. The ACK target applies
to the combined all-signal distribution. This is a reassessment of the existing
r4 run, with no rerun or new performance measurement:

- Sustained: 360.033323988 seconds, ACK p99 549.734201 ms, meeting the revised
  600 ms limit for the required 360 seconds.
- Burst: 60.000086519 seconds, ACK p99 526.834167 ms, meeting the unchanged
  1,000 ms limit for the full required 60 seconds at 2x load.
- Nine HTTP reads: maximum 6.694746643 seconds against 15 seconds inclusive.
  Three MCP reads: maximum 4.120590604 seconds against 5 seconds inclusive.
- Exact aggregate reconciliation passed for 6,436,200 durable contributions.
  Native Prometheus observed 676,200 samples, matching the expected count.
  Native delivery remains at least once; zero observed extras does not prove
  exactly-once semantics.
- Recorded readiness, drop/overflow and OOM checks passed. Final independent
  cleanup passed. The original result and its sustained-latency **FAIL against
  500 ms** remain unchanged.

The retained history was aged: 1,739 of 2,017 selected slots were present, with
five gaps. This run does not establish a fresh dense combined 2,016-window
history or a real seven-day soak. Separate physical seven-day aggregate and raw
capacity fixtures passed their scoped checks; their peaks were not measured
simultaneously. AKS/uk8s validation was excluded by the user and no deployment
was performed. These results do not certify full production readiness or the
absence of vulnerabilities.
