# v0.6.2 retention cleanup

SQLite retention batches now order traces and logs by `timestamp, id` and
spans by `start_time, id`. Empty expired ranges can use time indexes without
scanning retained rows to satisfy ID ordering. Orphan-span cleanup matches
both tenant ID and trace ID, using the existing trace identity index. A canceled
exemplar purge prevents the scheduler from starting its aggregate purge callback.

Main schema version 4 adds only `idx_spans_start_time` on `spans(start_time)`
for SQLite and PostgreSQL. The migration preserves existing data, optional FTS
objects, and migration 1-3 ledger entries. With `DB_AUTOMIGRATE=false`, startup
requires schema 4 and validates the index name, columns, and uniqueness; it
does not create or repair the index.

To upgrade, stop application writers and take a restorable database backup.
For SQLite, preserve the database and any WAL/SHM files coherently. Allow disk
space for the new index, its build, and the journal. Run the new binary's
`otelcontext migrate up` against the intended database, then
`otelcontext migrate status` and confirm `state=exact expected=4 actual=4`
before restarting writers.

An older binary expecting schema 3 refuses the upgraded ledger. To roll back,
stop writers and restore the pre-migration backup before starting that binary.
Restoring the backup discards writes made since it was taken. Do not remove
ledger entries or drop the index to bypass the compatibility check.

These changes address retention cleanup. Aggregate rollup and service-summary
query optimizations remain separate from this patch.
