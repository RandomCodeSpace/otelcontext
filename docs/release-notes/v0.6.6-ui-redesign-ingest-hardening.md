# v0.6.6 UI redesign and ingest hardening

This patch redesigns the web UI, makes OTLP ingestion stricter about trace and
span IDs, and removes SQLite stalls on topology reads. It adds one index to the
main schema. It does not change authentication, HTTPS termination, or the
aggregate schema.

## Upgrade

Stop application writers and take a restorable backup of the main database and
the separate aggregate database, if configured. Preserve SQLite databases and
their WAL/SHM files coherently, or use the supported backup procedure. Retain the
previous binary and configuration.

Using the new binary with the intended deployment's database configuration:

```sh
otelcontext migrate up
otelcontext migrate status
```

The main schema advances from 6 to **7**. Migration 7 adds only
`idx_spans_tenant_start` on `spans (tenant_id, start_time)`; rows, FTS objects
and earlier ledger entries are unchanged. SQLite and PostgreSQL use versioned
migrations; production startup with `DB_AUTOMIGRATE=false` requires the exact
schema and refuses a version-6 database with `state=behind expected=7 actual=6`.
MySQL and SQL Server receive the same index through AutoMigrate.

The index is built inside the migration transaction, so on PostgreSQL writes to
`spans` block while it builds. Allow free space for the index, its build sort
and journal: a 1M-span SQLite file (730 MB) took about 2.3 s and grew by 6.5%.

There is no down migration. A version-6 binary refuses the upgraded schema.
Rollback requires the previous binary/configuration and the pre-upgrade backup
restored into a separate target. Restoring an earlier backup omits writes
accepted after that backup.

## Client-visible ingestion changes

**Malformed IDs are refused.** A span needs a 16-byte trace ID and an 8-byte
span ID, neither all zero, and an empty or valid parent span ID. A log record's
IDs may be empty; present ones must be valid. Refused records are dropped before
sampling, graphs, aggregation, storage and the DLQ. The response still succeeds
for the rest of the batch and reports the exact count in `partial_success`
(`rejected_spans`, `rejected_log_records`) with a reason. Clients must not retry
it. A span link with a malformed ID is dropped and its span kept. Refusals are
counted on `otelcontext_ingest_rejected_total{signal,reason="invalid_id"}`.

**OTLP/JSON IDs are read as hex**, as the specification requires. Earlier
releases read them as base64, so spec-compliant JSON exporters lost every span
from the instance map. Senders that used base64 IDs are still accepted. Unknown
JSON fields are now ignored instead of failing the request with 400. Protobuf
requests were never affected.

Non-finite gauge and sum samples (NaN, ±Inf) are rejected before aggregate
reduction and reported in `partial_success`. `NO_RECORDED_VALUE` gap markers are
honored.

## Web UI

The UI is three full-viewport pages that share one design system:

- **Overview** at `/` is the new landing page: health summary, the services that
  need attention, a domain map, services by health, and storage and ingestion
  figures.
- **Service map** at `/service-map` lays out services, instances and hosts.
  Focusing a service shows its instances, their call edges, and the hosts they
  run on.
- **Explorer** at `/explorer` is the GraphRAG application map that used to live
  at `/`. Update bookmarks; its query parameters are unchanged.

## Fixes

- On SQLite, the graph rebuild, its tenant discovery and the first
  `/api/system/graph` request no longer scan every retained span while holding
  the only connection. On a 1.37M-span database the worst topology stall after
  startup fell from 4.9 s to 2 ms and the first system-graph response from
  14.7 s to 1.5 s; the old stalls produced 504s.
- Services known only from pre-sample topology no longer report `critical` right
  after startup.
- Explorer controls no longer cover service cards, and edge labels no longer sit
  on other edges.

## Verification limits

Unit, migration, browser, and PostgreSQL 16 lifecycle tests pass. The stall and
index figures come from local SQLite fixtures, not a production workload.
MySQL and SQL Server were not exercised live by this release work; the release
pipeline's database proof covers them. No seven-day soak is included.
